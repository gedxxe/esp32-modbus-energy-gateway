# Gateway engineering conventions

The gateway is an ESP32-C3 receiver for the ESP32-S3 Modbus power-meter node. The node repository is a separately versioned protocol peer; coordinated PTMP changes require explicit regression testing on both repositories. Its Energy Station protocol v1 defines the application packet format, byte order, authentication tag and telemetry contents. Do not add undocumented fields or commands to gateway frames. Firmware version numbers are independent from the radio protocol version. See `docs/NODE_COMPATIBILITY.md` and `docs/RADIO_DESIGN.md` for the current baseline.

The radio driver has one SPI owner. An interrupt handler only signals work. HTTP request handlers never touch the radio or flash directly: they enqueue bounded commands and use a published snapshot. The storage task reserves downlink POLL sequence numbers durably before transmission and validates checkpoint archives before committing them. Radio ACKs have priority over discretionary requests. Keep duplicate suppression, replay validation, per-node HMAC keys, a shared duty budget and complete request correlation in the production path. Do not use the public test-vector key for an installation.

Preserve the distinction between an accepted packet, a successful telemetry decode, a currently fresh sample and the last valid kWh reading. Missing or invalid energy must not become a numeric zero. The node performs Modbus scaling; the gateway consumes the already scaled kWh without applying PT/CT. Manual refresh and low-priority stale-data polling must not fabricate new readings or overwrite the last valid measurement when a newer packet has its energy-valid flag cleared.

Do not add personal workstation paths, login names, company Wi-Fi passwords, access codes, private keys, installation details or real meter secrets to code, tests, static assets, comments or release packages. Use relative paths and environment-neutral build commands. Test credentials are permitted only as clearly identified public vectors. Do not commit ELF/debug symbols, generated temporary files, proprietary site details or authentic device dumps. An ordinary commit cannot erase exposed data from historical commits.

The dashboard is an offline local engineering interface for Midea Engineering. Write conventional technical English or natural Indonesian rather than generic marketing slogans. Keep local data, timestamps, node-specific request states, errors and safety limitations clearly labeled. The logo/branding component must be bundled with the application and work without a CDN.

Run the native C++ regression suite with `python tools/test_native.py`, the dashboard tests in `dashboard/` with `npm ci && npm run build && npm test`, and the firmware build with `python -m platformio run --project-dir firmware -e esp32c3`. Rebuild the dashboard before compiling firmware because `firmware/include/web/assets.h` is generated from the React source. Firmware compilation and browser simulations are software evidence only. A successful real deployment requires physical SX1262/antenna tests, correlated POLL/TELEMETRY, a real Modbus power meter, brownout/reboot testing and multiple-node tests in the target factory.

## Folder topology

The PlatformIO project root is `firmware/`. Open that folder (not the repository root) in VS Code. Source code is under `firmware/src/`, reusable headers under `firmware/include/`, partitions and `platformio.ini` directly under `firmware/`, and VS Code extension settings in `firmware/.vscode/`. Host audit/build scripts, GitHub Actions, React frontend and shared documentation remain one level above. Do not reintroduce a root `platformio.ini` or point `src_dir` at the whole firmware tree.
